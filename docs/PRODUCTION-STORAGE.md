# Production evidence storage — Batch 6

The existing EvidenceStorage interface now supports local development storage and private S3-compatible storage. Delivery models, authorization, RLS, evidence keys and immutable history are retained. No signed URLs are issued: every byte retrieval continues through the authenticated evidence API, including tenant, capability and assigned-driver checks. Clients never receive provider locations or storage keys.

Set STORAGE_BACKEND=s3, S3_BUCKET and S3_REGION. S3_ENDPOINT is optional for AWS; custom endpoints require HTTPS. Inject S3_ACCESS_KEY and S3_SECRET_KEY together or use the standard SDK workload-identity credential chain. Never commit credentials. Explicit S3_ALLOW_INSECURE_LOOPBACK=true permits only localhost/127.0.0.1 HTTP for a disposable local drill, not an Internet provider.

Production startup requires S3 and the shared PostgreSQL limiter. No local fallback occurs. Startup/readiness check schema revision, database, bucket access/privacy and a write/read/delete probe. Public AllUsers/AuthenticatedUsers ACL grants and wildcard Allow bucket policies are rejected conservatively. Provider IAM must permit inspection; inability to establish privacy fails readiness. Bucket policy inspection is defense in depth: production operators must also block public access, disallow public object ACLs, isolate credentials and verify their actual provider. No deployment can prevent a privileged administrator from subsequently changing provider policies.

Runtime credentials need GetObject, PutObject, DeleteObject (uncommitted compensation/probes), ListBucket, bucket ACL/policy inspection and HeadBucket. Restrict these to one dedicated evidence bucket. Do not expose storage network endpoints or credentials to browsers. Use encryption at rest and provider audit logging according to the deployment's requirements. No provider configuration is silently created by application startup.

Opaque keys retain organization UUID/random evidence UUID, with no names. Strict key validation protects both providers. PutObject uses If-None-Match:*; unsupported conditional writes fail rather than falling back to overwrites. Reads are bounded to 5 MiB and checked against database SHA-256. SDK connect/read timeouts are 3/5 seconds with at most two attempts. Missing files produce a safe unavailable response; provider outages produce 503. Upload transactions register compensating deletion before storage writes. Failed cleanup emits a safe event and is discoverable by reconciliation; hard crashes cannot provide a distributed DB/object atomicity guarantee.

Existing validation is retained: JPEG/PNG/WebP, matching extension/MIME/decoded format, 5 MiB input/output, 16 million pixels, one frame, 12 retained objects per attempt. Pixel-only PNG normalization strips metadata and appended content. Superseded and historical evidence is retained. Object-store automatic expiration must not remove referenced objects.

Local integration uses an actual loopback Versity S3 Gateway 1.8.0, official checksum-verified Windows build, with persistent filesystem and sidecar metadata. This is not a mocked storage response. MinIO's official community download returned 410; no abandoned binary was substituted. Remote AWS/R2/B2 configuration, IAM, encryption, replication and recovery remain UNVERIFIED until deployed and tested.

References consulted: [AWS conditional PutObject](https://docs.aws.amazon.com/boto3/latest/reference/services/s3/bucket/put_object.html), [Versity gateway](https://github.com/versity/versitygw), [official quickstart](https://github.com/versity/versitygw/wiki/Quickstart).
